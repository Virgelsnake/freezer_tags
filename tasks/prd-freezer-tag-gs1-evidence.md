# Product Requirements Document: Freezer Tag GS1 Evidence Mode

**Project:** Freezer Tag POC  
**Version:** 0.1 draft for Codex Bridge  
**Created:** 2026-05-28  
**Owner:** DTP / Hudson  
**Current baseline:** Domestic PoC delivers label, freeze, retrieve, update, clear and reuse one container. Steve has physically confirmed NFC cards work and work through the container.  
**Target next version:** Market-facing GS1-style operational evidence demo.

---

## 1. Purpose

Freezer Tag GS1 Evidence Mode should reposition the app from a domestic freezer helper into a small operational proof for food businesses that need to associate physical items with traceable product information and produce lightweight evidence of checks.

The point is not to claim full regulatory, food-safety, GS1 certification, or chain-of-custody proof. The point is to show a credible workflow:

> scan an item, record a check note, create an exportable evidence line, and state the proof limit.

This version should demonstrate how NFC could support a GS1-compatible audit trail around labelled food items, batches, or containers.

---

## 2. Product goal

Build a second app mode or variant focused on operational evidence for GS1-compliant market use.

The user should be able to:

1. Upload or import the product/item information they want associated with an NFC tag.
2. Validate that the supplied data has the core identifiers needed for a GS1-style item record.
3. Write a compact identifier or payload to the NFC tag.
4. Scan a tagged item during an operational check.
5. Record a dated check note.
6. Export a tamper-evident-ish evidence line for audit review.
7. See a plain-English statement of what the evidence proves and what it does not prove.

This is a market-application PoC, not a certified compliance product. Do not let the UI imply more proof than the system actually has. Compliance goblin stays in its box.

---

## 3. Primary operational script

### Script name

**Operational check: scan, note, export, proof limit**

### Demo flow

1. Operator opens the app in GS1 Evidence Mode.
2. Operator imports or selects a product/item record.
3. Operator writes/links that record to an NFC tag.
4. Operator scans the physical tagged item or box.
5. App displays the item identity, batch/lot, dates and current tag status.
6. Operator records a check note, for example:
   - visual check complete;
   - temperature check recorded elsewhere;
   - label present;
   - item moved to freezer;
   - item retrieved for dispatch;
   - item quarantined;
   - correction made.
7. App creates an evidence event containing who/what/when/source fields.
8. Operator exports the evidence line as CSV and JSON.
9. App displays a proof-limit statement before or after export.

### Required proof-limit statement

The app must show this concept in clear wording:

> This evidence shows that this device scanned this NFC tag and recorded this check note at this time using the data stored in this app. It does not prove the food itself was safe, that the tag was never moved, that the operator performed the check correctly, or that the record meets every legal or GS1 compliance requirement.

The exact wording can be refined, but the limitation must remain visible and honest.

---

## 4. Target users

### Primary user: food operations operator

Someone working in a small food production, meal prep, catering, cold-chain, or prepared-food environment who needs to evidence item-level or batch-level checks.

They are not a GS1 standards expert. They need guided fields, validation, and plain-English warnings.

### Secondary user: operations manager or auditor

Someone reviewing evidence after the fact. They need exportable records with consistent fields and enough context to understand whether the evidence is useful.

## 5. Data model

### Product or item master record

The app must support a product/item record uploaded by the user. Minimum fields:

- `record_id`: internal UUID generated by the app.
- `gtin`: product identifier, if supplied.
- `product_name`: required.
- `brand_or_supplier`: optional.
- `batch_or_lot`: recommended for operational evidence.
- `serial_or_item_id`: optional, for item-level tracking where available.
- `expiry_or_use_by_date`: optional but strongly recommended.
- `packed_or_frozen_date`: optional.
- `quantity_or_pack_size`: optional.
- `storage_state`: optional enum, for example ambient, chilled, frozen.
- `storage_instruction`: optional text.
- `allergen_summary`: optional text, only if supplied by the user.
- `source_file_name`: file name of uploaded source, if applicable.
- `source_imported_at`: timestamp.
- `source_hash`: hash of the imported source row or file if feasible.
- `created_at`, `updated_at`.

### NFC tag link record

The app must track the relationship between a physical tag and the product/item record.

Fields:

- `tag_id`: NFC tag UID or stable readable identifier where available.
- `ndef_payload`: payload written to tag.
- `payload_type`: enum, for example `gs1_digital_link`, `app_record_pointer`, `plain_json_demo`.
- `record_id`: internal record linked to the tag.
- `linked_at`.
- `linked_by`: local operator name or device profile, if available.
- `tag_status`: active, replaced, cleared, retired, unknown.
- `placement_note`: optional note, for example outside box, lid, label area.

### Check event / audit evidence record

Every scan/check must create an event record.

Fields:

- `event_id`: UUID.
- `event_type`: check, write, update, clear, export, exception.
- `event_timestamp`: local timestamp with timezone.
- `operator_name`: local app setting or user-entered value.
- `device_label`: local device/app label if available.
- `tag_id`.
- `record_id`.
- `gtin`, `batch_or_lot`, `serial_or_item_id`, `expiry_or_use_by_date`, where available, copied into the event snapshot.
- `check_note`: required for check events.
- `check_status`: optional enum, for example pass, concern, fail, note only.
- `location_note`: optional free text, no GPS required for this PoC.
- `payload_read`: what was read from the tag.
- `payload_hash`: hash of payload read, if feasible.
- `previous_event_hash`: optional hash chain field for demo tamper-evidence.
- `event_hash`: hash of canonical event content, if feasible.
- `proof_limit_version`: version of the proof-limit wording shown to the user.

## 6. GS1 handling

### Required stance

The app should be **GS1-compatible in data shape and language**, not presented as formally GS1-certified.

Use GS1 terminology carefully:

- GTIN for product identity, where supplied.
- Batch/lot for production batch, where supplied.
- Serial/item ID for item-level uniqueness, where supplied.
- Expiry/use-by date for date-sensitive food evidence, where supplied.
- GS1 Digital Link URI as an optional payload format where enough fields exist.

### Payload strategy

The app should support at least two payload modes:

1. **GS1 Digital Link demo payload**
   - Write a URI-style payload based on supplied identifiers when possible.
   - Include GTIN and optional batch/lot, serial, and date values only where supplied.
   - Do not invent missing identifiers.

2. **App record pointer payload**
   - Write a compact internal record pointer to the tag.
   - Full data remains in local app storage.
   - Evidence export includes both tag payload and app-side record snapshot.

The implementation should prefer the compact pointer payload if tag capacity is tight. The UI should explain the trade-off.

### Validation

When importing or entering data, the app should flag:

- missing product name;
- invalid or obviously malformed GTIN length/check digit if validation is implemented;
- missing batch/lot for batch evidence;
- missing expiry/use-by date for perishable food evidence;
- payload too large for the tag;
- use of non-food-contact tag placement if the tag is intended to sit inside packaging.

Validation should warn, not block everything. A PoC can continue with incomplete fields, but the export must show warnings.

## 7. Upload/import requirements

The user needs a way to upload the information they want written or linked to the card so there is an audit trail.

### Import formats for PoC

Support at least one of:

- CSV import via iOS document picker.
- JSON import via iOS document picker.
- Manual single-record entry form.

Preferred for Codex implementation: start with manual entry plus CSV import if feasible. If file import risks slowing the build, implement manual entry first and create import-ready model/service boundaries.

### CSV fields

Suggested headers:

```csv
gtin,product_name,brand_or_supplier,batch_or_lot,serial_or_item_id,expiry_or_use_by_date,packed_or_frozen_date,quantity_or_pack_size,storage_state,storage_instruction,allergen_summary
```

The app must:

- preserve the source row values as imported;
- show import warnings;
- create a local `source_hash` for the imported row or file if feasible;
- avoid silently changing supplied values;
- allow the user to select one imported item to link to a tag.

## 8. Functional requirements

### FR1. Mode selection

The app must expose GS1 Evidence Mode separately from the domestic container flow, either via a home-screen mode switch, separate tab, or separate entry point.

Acceptance:

- User can enter the GS1 operational flow without breaking the existing domestic PoC.
- Existing domestic flow remains available unless implementation scope explicitly creates a separate target/app variant.

### FR2. Product/item record creation

The app must allow manual creation of a product/item record with the minimum fields listed above.

Acceptance:

- Product name is required.
- GTIN, batch/lot, serial/item ID and dates can be entered when available.
- Missing recommended fields generate warnings.

### FR3. Product/item import

The app should allow CSV or JSON import where feasible.

Acceptance:

- User can select an import file.
- App parses records into local storage.
- Import warnings are visible.
- Source file name and import timestamp are captured.

If this is too much for the first implementation pass, Codex must preserve the data model seams and mark import as an explicit follow-up rather than pretending it is done.

### FR4. NFC tag write/link

The app must let the user write or link a selected record to an NFC tag.

Acceptance:

- User selects a record.
- App chooses payload mode or allows user to choose payload mode.
- App writes the payload or records the link.
- App creates a write/link evidence event.
- App handles tag write errors clearly.

### FR5. Scan operational item

The app must let the user scan a tag and resolve it to the associated product/item record.

Acceptance:

- App reads the tag.
- App shows product name, GTIN if present, batch/lot if present, expiry/use-by if present, and tag status.
- App warns if the tag is unknown, retired, cleared, or payload cannot be resolved.

### FR6. Record check note

After a scan, the app must prompt the user to record a check note.

Acceptance:

- Check note is required for a check event.
- Optional status can be selected: pass, concern, fail, note only.
- Event snapshot is saved locally.
- The saved event includes the payload/tag data read at scan time.

### FR7. Export evidence line

The app must export evidence events as CSV and JSON, or at least generate/export one of those formats with the model designed for both.

Acceptance:

- Export includes one row/object per event.
- Export includes event timestamp, operator/device, tag ID, payload, product/item identifiers, check note, warnings, and proof-limit version.
- Export can be shared using native iOS share sheet.

### FR8. Proof-limit display

The app must show proof-limit wording in the check/export flow.

Acceptance:

- User sees the proof limit before export or in the export review screen.
- Export includes a proof-limit field or reference.
- Wording is plain English and does not overclaim compliance.

### FR9. Audit trail viewer

The app should include a local audit/event history view.

Acceptance:

- User can see recent write, scan/check, clear and export events.
- Events show timestamp, product/item, operator, status and note.
- Events are read-only in the UI for this PoC.

### FR10. Tag lifecycle

The app should support clearing, replacing, retiring, or reusing a tag with an audit event.

Acceptance:

- Clearing or reassigning a tag prompts for confirmation.
- Action creates an event.
- History is retained locally unless the user explicitly deletes demo data.

## 9. UX requirements

The app should feel operational, not domestic.

Recommended screens:

1. **Mode/home screen**
   - Domestic PoC entry.
   - GS1 Evidence Mode entry.

2. **GS1 evidence dashboard**
   - Import/create record.
   - Write/link NFC tag.
   - Scan item/check.
   - Evidence history/export.

3. **Record detail screen**
   - Product/item identifiers.
   - Warnings.
   - Linked tag status.
   - Actions: write/link tag, scan/check, view events.

4. **Scan/check screen**
   - NFC scan prompt.
   - Resolved item summary.
   - Check note and status.
   - Save event.

5. **Evidence export screen**
   - Event list or selected event.
   - Export format.
   - Proof-limit statement.

Use plain labels. Avoid making the user decode GS1 jargon before the value is clear.

## 10. Non-goals

This version must not attempt to deliver:

- Formal GS1 certification.
- Legal food-safety compliance advice.
- HACCP plan generation.
- Temperature sensor integration.
- Blockchain, because no. Absolutely not unless Steve explicitly insists while holding a tiny ceremonial shame bell.
- Multi-user cloud identity.
- Backend sync.
- Tamper-proof chain of custody.
- Proof that a tag was not removed from one box and placed on another.
- Proof that the food itself is safe.
- Automatic regulatory reporting.
- Customer-facing production deployment.

## 11. Technical considerations

### Existing app preservation

Do not break the domestic flow. Add the GS1 market application as either:

- a separate mode inside the same app, preferred for fastest PoC; or
- a separate target/branch if the app structure makes this cleaner.

### Persistence

Use existing local persistence patterns if possible. Add new models for product/item records, tag links, and evidence events.

### Hashing

If straightforward in Swift, add canonical JSON serialization and SHA-256 hashes for:

- imported source row or file;
- payload read/written;
- event content;
- optional previous event hash.

If hashing would add too much risk in the first pass, create deterministic event IDs and leave hashing as a clearly documented follow-up.

### Export

Use native iOS share sheet for CSV/JSON export if feasible. At minimum, implement deterministic export string generation with unit tests.

### NFC constraints

Tag memory is limited. Store compact identifiers on the tag where possible. Do not write large JSON blobs unless capacity is checked.

### Food-contact safety note

The app should include a note that NFC tag placement is a packaging/food-contact decision. For the current Amazon PVC cards, use them for PoC/dev only, not customer-facing placement inside food boxes unless compliant food-contact documentation is obtained. Prefer external tag placement for the demo.

## 12. Acceptance criteria

### AC1. GS1 Evidence Mode exists

- App has a visible path into GS1 Evidence Mode.
- Existing domestic PoC still builds and remains accessible.

### AC2. Product/item record can be created

- User can create a record with product name and optional GS1-style identifiers.
- Missing recommended fields produce warnings.
- Record persists locally.

### AC3. Tag can be linked/written

- User can link a selected record to an NFC tag or simulated NFC path.
- A write/link event is recorded.
- Errors are visible and recoverable.

### AC4. Scan/check/evidence line works

- User scans a tag.
- App resolves the item.
- User records a check note.
- App saves an evidence event.
- Event contains tag, item snapshot, timestamp and note.

### AC5. Export works

- User can export evidence as CSV or JSON.
- Export includes proof-limit field/warning.
- Export generation is unit-tested independent of NFC hardware.

### AC6. Proof limit is explicit

- The app displays proof-limit wording in the check/export flow.
- The wording does not claim food safety, tamper-proofing, operator truthfulness, or formal compliance.

### AC7. Simulator-verifiable core logic

- Data model, validation, event creation, proof-limit string, and export generation are covered by tests.
- NFC-dependent operations have clear manual test notes.

## 14. Definition of done for Codex Bridge pass

Codex should deliver a buildable, testable implementation pass that creates the GS1 Evidence Mode skeleton and the core simulator-verifiable logic.

Minimum done:

- New GS1 Evidence Mode is reachable from the app.
- Domestic flow still builds.
- Product/item records, tag link records and evidence events exist as testable models.
- User can create a demo product/item record manually.
- User can record a scan/check event through either real NFC where already supported or a simulator/demo path that is clearly labelled.
- CSV or JSON export generation works and is tested.
- Proof-limit statement is visible and included in export.
- Unit tests cover validation and export generation.
- README or docs explain what is proven, what is simulated, and what still needs physical NFC/customer compliance validation.

If Codex cannot safely implement all of this in one pass, it should prioritise the data model, validation, evidence event, proof-limit and export generator first, then leave UI/import/NFC integration as explicit follow-up tasks with file paths and acceptance tests.
